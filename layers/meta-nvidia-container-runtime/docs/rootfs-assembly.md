# Rootfs assembly

Five `IMAGE_PREPROCESS_COMMAND` functions in
`recipes-core/images/balena-nvidia-runtime.bb` shape the extension rootfs. Each
exists because of a failure that produced **no build error and no merge error**,
and a runtime symptom pointing somewhere else entirely. That is why several of
them log `bbnote` lines that would otherwise look like noise.

They run in this order; `assert_no_kernel_modules` must come after
`strip_kernel_modules`, and `link_passthrough_canonical_paths` must come after
anything that removes files.

## `strip_var_except_nvidia`

`/var` is kept out of `HOSTAPP_EXTENSION_REMOVE_PATHS` because of `/var/nvidia`
(the ISP tuning data — see [design.md](design.md#paths-kept-out-of-the-strip-list)),
but nothing else under it should ship: the hostapp underneath owns `/var/log`,
`/var/lib` and friends. So filter rather than keep wholesale.

The before/after `bbnote` pair is deliberate. This content going missing is
invisible until a camera client connects, so having the build log state what
survived is worth two lines.

## `strip_kernel_modules`

**This is the failure mode the layer is most designed against.**

`tegra-libraries-camera`'s RDEPENDS chain drags in V4L2 framework kernel modules
(`videobuf2-*.ko.zst`, `mc.ko.zst`, `v4l2-async.ko.zst`, …) without being asked.
Their mere presence in the extension rootfs trips mobynit's `FilterByKernelABIID`
at boot, which then demands an `io.balena.image.kernel-abi-id` label. The bbclass
only stamps that label for a real kernel-override extension (`Module.symvers` plus
a kernel image in `/boot`), and this extension is neither.

So the label is absent, **mobynit silently drops the extension from the rootfs
lowerdir, and the install looks clean (rc=0) while the overlay never merges.**

Bisected during the PoC to balena-jetson-orin commit `934b50c` / release `235279`,
2026-06-09.

The modules are not needed: the base OS kernel already provides them.

## `assert_no_kernel_modules`

Backstop for the above. `strip_kernel_modules` only knows the four paths that have
bitten us; this sweeps the whole rootfs for any module content at all, so a future
dependency landing modules somewhere new **fails the build loudly** instead of
shipping an extension that silently refuses to merge on device.

## `strip_unused_toolkit_binaries`

The `nvidia-container-toolkit` recipe builds every command in the upstream tree
(`GO_INSTALL = "${GO_IMPORT}/cmd/..."`), including two sizeable binaries this
layer has no route to:

| Binary | Size | Why it goes |
|---|---|---|
| `nvidia-cdi-hook` | ~7 MB | only ever invoked from a CDI spec, and we generate none |
| `nvidia-ctk-installer` | ~13 MB | installs the toolkit *into* a container (the GPU-operator flow); not how extensions work |

Dropping them makes "legacy route only" an enforced property rather than an
intention, and takes ~20 MB off every device's download.

**Deliberately not dropped:** `nvidia-container-runtime.cdi`. It belongs to the
runtime's own mode-dispatch family alongside `nvidia-container-runtime.legacy`, and
the saving is not worth risking how the main binary resolves its mode.

## `link_passthrough_canonical_paths`

Makes meta-tegra's canonical-path tree resolvable at the host root.

A Yocto host has a flat `${libdir}` (`/usr/lib`), but the container CSVs reference
Debian multiarch paths
(`/usr/lib/aarch64-linux-gnu/{nvidia,gstreamer-1.0,libv4l}/…`) because they are
authored for a stock L4T/Ubuntu rootfs. meta-tegra bridges that with
`tegra-container-passthrough`, which ships a mirror of the canonical layout under
`/usr/share/nvidia-container-passthrough/`.

That tree is only consumed by `nvidia-ctk cdi generate --alt-roots=…`. meta-tegra's
alt-roots patch wires the flag into the CDI generator and adds a matching config
field, but **nothing passes the config value into the runtime's CSV modifier** — so
on the legacy route every canonical CSV entry silently resolves to nothing.
Confirmed on device: with alt-roots set and mode forced to csv, the container still
had no `/usr/lib/aarch64-linux-gnu/gstreamer-1.0`. The PoC never hit this because
it drove the CDI generator directly, passing `--alt-roots` itself.

So bridge it here: link every file the passthrough tree provides into its canonical
location, letting the hook find it at `/`. Generated by walking the tree rather
than hand-listing paths, so it survives L4T bumps. Per-file links, not directory
links — shadowing a whole directory would hide anything the real rootfs already has
there (e.g. `tegra-egl`). Existing paths are never overwritten.

### Hardlinks, not symlinks

This matters and was got wrong once. The CSV locator **resolves symlinks and then
uses the resolved path as the container destination**, not the path it started
from. With symlinks the runtime logged:

```
Located   /usr/lib/aarch64-linux-gnu/gstreamer-1.0/libgstnvarguscamerasrc.so
       as [/usr/share/nvidia-container-passthrough/usr/lib/.../libgstnvarguscamerasrc.so]
Selecting /usr/share/nvidia-container-passthrough/usr/lib/.../libgstnvarguscamerasrc.so
       as /usr/share/nvidia-container-passthrough/usr/lib/.../libgstnvarguscamerasrc.so
```

i.e. it mounted the library into the container under the *passthrough* path rather
than the canonical one, so nothing appeared at
`/usr/lib/aarch64-linux-gnu/gstreamer-1.0/`.

A hardlink is indistinguishable from a real file, so the locator finds it directly,
resolves nothing, and mounts it at the canonical path — which is exactly why the
flat `/usr/lib` entries worked from the start. Costs no space: same inode, same
filesystem. The image already carries hardlinks elsewhere (e.g.
`libEGL_nvidia.so.0`).

Symlinks *within* the passthrough tree are recreated as symlinks, keeping their
original relative target so they resolve against the canonical directory they land
in.

### The one entry deliberately not created

The bare `sym, /usr/lib/aarch64-linux-gnu/tegra` CSV entry. It wants a symlink to
the driver library directory, which for us is `/usr/lib` — and
`/usr/lib/aarch64-linux-gnu/tegra -> /usr/lib` is a **symlink loop** on the host
rootfs, since `/usr/lib` contains `aarch64-linux-gnu`. Fine inside a container,
which is why the PoC's CDI `--link` worked, but here it would be walked by image QA
and by host tooling. Left for a targeted fix if an L4T-native container ever needs
it.

## The four camera fixes

Camera capture required four changes that **only work together** — none produces a
visible change alone, which caused several misleading single-variable tests:

| Fix | Without it |
|---|---|
| `mode=csv` forced in the boot oneshot | CSVs never read; no mounts at all |
| Hardlinks (not symlinks) for canonical paths | libs mount under the passthrough path, invisible to the loader |
| `libnvmm_jpeg.so` added to `drivers.csv` | `nvarguscamerasrc` will not load |
| `/var/nvidia` preserved | `nvargus-daemon` SIGABRTs the moment a client connects |

## A note on bitbake's shell parser

No arithmetic expansion anywhere in these functions: bitbake's `pysh` raises
`NotImplementedError` on `$(( ))`.
